# Garager — планировщик ТО для личного авто

> SPA для отслеживания регламентных работ автомобиля: замены масла, фильтров, ремней и т.д.
> Задачи можно планировать **по пробегу** или **по дате**, переключаться между двумя режимами отображения, вести историю выполненных работ и хранить несколько машин под одним аккаунтом.

Статус: **pet-проект для портфолио**. Бэкенда нет — данные эмулируются через mock-слой поверх `localStorage`, что позволяет демонстрировать фичи без инфраструктуры.

## Архитектура состояния

Стейт разделён на три слайса + один RTK Query API. Каждый слайс отвечает за одну зону ответственности:

```
store/
├── slices/
│   ├── userSlice.ts      // авторизация, тема, режим отображения (dimension)
│   ├── carSlice.ts       // список машин, выбранная машина
│   └── uiSlice.ts        // открытые модалки, selectedTaskId, prefill-данные
├── utils/
│   └── taskApi.ts        // RTK Query endpoints (CRUD задач, mock fetchUser)
└── hooks/
    └── hooks.ts          // типизированные useAppDispatch / useAppSelector
```

### Поток данных

```
UI (компонент)
  └─ dispatch(action) ──► Redux store (user/car/ui slices)
                              ├─ persist to localStorage (внутри редьюсеров)
                              └─ RTK Query (taskApi)
                                     └─ fetchBaseQuery поверх localStorage
                                            └─ возвращает/мутирует данные
```

### `userSlice`

| Поле | Тип | Назначение |
|------|-----|-----------|
| `user` | `TUser \| null` | Текущий залогиненный пользователь (token, name, email) |
| `theme` | `'light' \| 'dark'` | Тема оформления |
| `dimension` | `'mileage' \| 'date'` | Режим отображения задач: по пробегу или по дате |

**Редьюсеры:** `updateProfile` (меняет name/email, синхронно обновляет массив `users` в localStorage, при смене email переносит ключи `cars` и `tasks`), `logout` (чистит `user` из state и localStorage).

### `carSlice`

| Поле | Тип | Назначение |
|------|-----|-----------|
| `cars` | `Car[]` | Список машин пользователя |
| `carSelected` | `Car \| null` | Активная машина (`null` — ничего не выбрано) |

**Дизайнерские решения:**

- `cars: Car[]` вместо `Car[] | null` — пустой массив это валидный `Car[]`, проверка на null в каждом компоненте избыточна.
- `carSelected: Car | null` вместо `boolean` — однозначно указывает на выбранную машину, а не просто факт выбора.
- Слайс спроектирован под **массив машин** с самого начала, хотя MVP работает с одной. Это позволяет добавить вторую машину без рефакторинга редьюсеров.

### `uiSlice`

Хранит UI-состояние, не имеющее бизнес-семантики: `selectedTaskId` (какая задача открыта в модалке), флаги открытых модалок, prefill-данные для форм.

## Данные и типы

### `Task`

```typescript
interface Task {
  id: number;
  text: string;              // ≤ 25 символов (валидация)
  description?: string;
  targetMileage: number;     // целевой пробег (0, если задача по дате)
  targetDate: string | null; // ISO-дата (null, если задача по пробегу)
  actualMileage?: number;    // фактический пробег на момент выполнения
  isDone: boolean;
  carId: string;             // привязка к машине
  completedAt?: string | null; // ISO-дата выполнения (для истории)
}
```

### `Car`

```typescript
interface Car {
  id: string;
  name: string;
  mileage: number;
}
```

### `TUser`

```typescript
interface TUser {
  token: string;
  name: string;
  email: string;
}
```

### Логика отображения статуса задачи

Главная бизнес-логика — корректный статус задачи в зависимости от режима `dimension` и наличия данных:

| Условие | Что показываем |
|---------|---------------|
| `isDone === true`, `actualMileage > 0` | `Выполнено на 12 345 км` |
| `isDone === true`, `actualMileage === 0` | `Выполнено 01.02.2026` |
| `dimension === 'date'`, есть `targetDate` | `до 01.02.2026` / `Просрочено (до 01.02.2026)` |
| `dimension === 'mileage'`, `targetMileage > 0` | `Через: 5 000 км` / `Просрочено на 500 км!` |
| `dimension === 'mileage'`, но `targetMileage === 0` и есть `targetDate` | **Fallback на дату** — задача создана в режиме даты, переключение режима не должно ломать её отображение |
| Нет ни пробега, ни даты | `Без срока` |

**Ключевой инсайт:** задача, созданная в режиме даты (`targetMileage: 0`), при переключении юзера в режим пробега **не должна** показывать «Через: 0 км». Реализовано через проверку `task.targetMileage > 0` перед расчётом remaining-пробега и fallback-веткой на дату.

## Mock-сервер (RTK Query + localStorage)

Бэкенд эмулируется через `fetchBaseQuery` с переопределённым `queryFn`, который читает/пишет `localStorage`. Это позволяет использовать **весь** инструментарий RTK Query (кеш, теги, `isLoading`, инвалидация) без реального сервера.

### Endpoints в `taskApi.ts`

```typescript
useGetTasksQuery()         // GET /tasks — чтение всех задач из localStorage
useAddTaskMutation()       // POST — добавление задачи
useUpdateTaskMutation()    // PATCH — обновление полей (включая isDone, completedAt)
useDeleteTaskMutation()    // DELETE — удаление задачи
```

### `fetchUser` (thunk, не endpoint)

Авторизация реализована через `createAsyncThunk`, а не RTK Query endpoint — намеренно, чтобы отделить «auth-флоу» от CRUD-слоя:

```typescript
export const fetchUser = createAsyncThunk<TUser, UserLogin>(
  'user/login',
  async (loginData) => {
    await new Promise(resolve => setTimeout(resolve, 1500)); // имитация сети
    const existingUsers = JSON.parse(localStorage.getItem('users') || '[]');
    const foundUser = existingUsers.find(u => u.email === loginData.email);
    if (!foundUser) throw new Error('Пользователь не найден');
    if (foundUser.password !== loginData.password) throw new Error('Неверный пароль');
    return {
      token: generateId(),           // новый токен при каждом входе
      name: foundUser.name,          // актуальное имя из базы
      email: foundUser.email
    };
  }
);
```

**Важный момент:** `fetchUser` ищет пользователя в массиве `users` и возвращает его **актуальное** имя. Если в профиле имя поменяли, `updateProfile` синхронно обновляет `users`, и при следующем входе `fetchUser` вернёт свежее имя. Раньше здесь был хардкод — это был основной баг «старое имя после перелогина».

### Инвалидация кеша

`useUpdateTaskMutation` и `useDeleteTaskMutation` инвалидируют тег `'Task'`, что автоматически вызывает `useGetTasksQuery` на перечитывание. Никаких ручных `dispatch(refetch())`.

## Multi-user

Поддержка нескольких пользователей реализована полностью на клиенте:

- `localStorage.users` — массив всех зарегистрированных пользователей (`{ name, email, password }`).
- `localStorage.user` — текущий залогиненный пользователь (`{ token, name, email }`), очищается при `logout`.
- `localStorage.cars` и `localStorage.tasks` хранят данные **всех** пользователей вперемешку, фильтрация по `carId` / текущему `user` происходит на уровне selectors.

### Привязка данных к пользователю

- **Машины:** ключ `cars` хранит массив всех машин, каждая машина имеет `id`. `carSelected` указывает на активную.
- **Задачи:** каждая задача имеет поле `carId`, что позволяет фильтровать задачи по выбранной машине:

```typescript
const inWorkTasks = (data || [])
  .filter(t => !t.isDone && t.carId === currentCarId)
  .sort((a, b) => (a.targetMileage - currentMileage) - (b.targetMileage - currentMileage));
```

### Смена email

При смене email в профиле `updateProfile` переносит ключи `cars` и `tasks` в localStorage, чтобы данные пользователя не «отваливались» после смены логина.

## Кастомные хуки

### `useAppDispatch` / `useAppSelector`

Типизированные обёртки над стандартными Redux-хуками, чтобы не указывать `RootState` и `AppDispatch` типы в каждом вызове:

```typescript
export const useAppDispatch = () => useDispatch<AppDispatch>();
export const useAppSelector: TypedUseSelectorHook<RootState> = useSelector;
```

Это стандартный паттерн из документации RTK, но он обязателен: без него `dispatch(someThunk())` не типизируется корректно (ThunkAction не выводится).

### Хуки в компонентах

- `useState` для локального UI-стейта (редактируемый текст, режим edit, ошибки валидации).
- `useAppSelector` для чтения Redux-state.
- `useEffect`-паттерны минимальны — большинство данных приходит через RTK Query, который сам управляет жизненным циклом запроса и кеша.

## Ключевые решения по оптимизации

### 1. Сортировка и фильтрация при рендере

Сортировка `inWorkTasks` (ближайшие ТО по remaining-пробегу) и `isDoneTasks` (последние выполненные сверху) считается в `Tasks.tsx` прямо при рендере, потому что:

- Массив задач пользователя мал.
- Сортировка идёт после `filter` по `carId`, поэтому работает с уже урезанным набором.

### 2. Persist в localStorage внутри редьюсеров, а не через middleware

Вместо подключения `redux-persist` (лишняя зависимость + сложность настройки под несколько ключей), персист сделан прямо в редьюсерах (`updateProfile`, `logout` и т.д.). Это:

- Делает поток данных линейным и читаемым: `dispatch → reducer → localStorage.setItem`.
- Упрощает отладку: в DevTools видно каждое изменение.
- Для pet-проекта с 3 слайсами это оправдано.

### 3. Inline-валидация с локальным стейтом

Инпуты (название задачи, пробег, описание) хранят локальный draft в `useState` и отправляют в Redux только по `onBlur`, если значение прошло валидацию. Это:

- Снижает количество dispatch'ей (не на каждое нажатие клавиши).
- Позволяет показать ошибку валидации **до** сохранения.
- Даёт UX «отмена правки» — можно уйти из инпута без сохранения, просто переключившись.

### 4. `completedAt` хранится в задаче, а не выводится из `new Date()`

Дата выполнения задачи сохраняется в момент клика «Задача выполнена» (`completedAt: new Date().toISOString()`), а не вычисляется при каждом рендере через `new Date()`. Иначе дата «сегодня» менялась бы при каждом перезаходе в приложение.

### 5. Защита выполненных задач от редактирования

В `TaskModalContent` инпуты переключаются в `variant='disabled'`, когда `task.isDone === true`. Кнопка «Задача выполнена» не рендерится для уже выполненных задач. Историю нельзя случайно изменить.

### 6. Fallback логики режима отображения

Переключение `dimension` (mileage ↔ date) не ломает отображение задач, созданных в другом режиме. Это намеренное UX-решение: пользователь не должен «страдать» от того, что задача была создана в режиме даты, а сейчас включён режим пробега.

## Временные решения

Эти решения **осознанно упрощены для pet-проекта** и помечены как неприемлемые для production:

### 1. Пароли в открытом виде в `localStorage`

Пароли хранятся в `localStorage.users` в plain text. В реальном проекте:

- Хэширование на бэкенде (bcrypt / argon2).
- Никогда не хранить пароли на клиенте.

### 2. Токен генерируется заново при каждом входе

Токен — это просто `generateId()`, он не валидируется на сервере и не имеет срока жизни. В реальном проекте:

- JWT с подписью и expiration.
- Refresh-token flow.

### 3. Нет настоящей авторизации на бэкенде

Любой пользователь с доступом к DevTools может читать/писать `localStorage` других пользователей (в рамках одного браузера). Это нормально для демонстрации фич, но не для real-world multi-tenant.

### 4. Mock-слой поверх `localStorage` вместо бэкенда

`fetchBaseQuery` переопределён через `queryFn`, который работает с `localStorage`. Ограничения:

- Нет совместного доступа с других устройств.
- Нет real-time обновлений (нужен polling).
- Данные теряются при очистке браузера.

Запланированный переход — на реальный бэкенд (см. [Дальнейшее развитие](#дальнейшее-развитие)).

### 5. `setTimeout(resolve, 500)` в `fetchUser` для имитации сети

Задержка добавлена намеренно, чтобы демо показывало состояния `isLoading` (скелетоны, спиннеры). В production это убирается.

### 6. Нет unit/e2e тестов

Pet-проект пока не покрыт тестами. Для портфолио это допустимо, но для production обязательно: Vitest для логики (валидаторы, селекторы), Testing Library для компонентов, Playwright для e2e.

### 7. Хранение `cars` и `tasks` в общем ключе без индексации

Все задачи всех пользователей лежат в одном массиве в `localStorage.tasks`, фильтрация по `carId` идёт на клиенте. При росте данных это O(n) на каждый рендер. В реальном бэкенде — индекс по `carId` и фильтрация на SQL-уровне.

### 8. Нет обработки гонок при записи в `localStorage`

Если два таба одновременно меняют данные, возможна потеря обновлений. В pet-проекте это не критично, в production — нужен optimistic concurrency control или серверная валидация.

### 9. Стилизация через `!important` для disabled-состояний

В `Item.module.scss` для переопределения hover-эффектов иконки внутри disabled-кнопки используется `!important`. Это компромисс: компонент `Button` и класс `.icon` имеют свои hover-стили, и без `!important` их приходится перебивать через специфичность. В большой кодбазе это стало бы проблемой, в pet-проекте — приемлемо.
